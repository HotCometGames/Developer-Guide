# Learning & Growth

> How to get better at software engineering — systematically and sustainably.

## What Is It?

Software engineering changes fast. The most valuable skill is learning how to learn — efficiently and with lasting retention.

## The 70-20-10 Model

| Source | % | How |
|--------|---|-----|
| Experience | 70% | Build projects, solve real problems, ship code |
| Others | 20% | Code reviews, pair programming, mentoring, reading code |
| Formal | 10% | Courses, books, documentation, conferences |

Most growth comes from doing, not studying.

## Deliberate Practice

Not all practice is equal. Deliberate practice is:

| Characteristic | What It Means |
|----------------|---------------|
| Specific goal | "Learn async/await in Python" not "learn Python better" |
| At your edge | Challenging but not impossible |
| Immediate feedback | Tests, code review, or a mentor |
| Repeatable | Practice the same skill until it's automatic |
| Focus on weakness | Spend time on what you're bad at, not what you're good at |

## Career Stages

| Stage | Focus | Key Activities |
|-------|-------|----------------|
| **Junior** | Syntax, tools, basics | Build things, follow tutorials, learn the stack |
| **Mid-level** | Patterns, architecture, trade-offs | Read code, contribute to reviews, own features |
| **Senior** | System design, mentoring, strategy | Lead projects, write RFCs, unblock others |
| **Staff+** | Org impact, technical vision | Cross-team initiatives, ADRs, set technical direction |

## Reading Code

Reading well-written code is one of the fastest ways to improve:

| Source | What to Look For |
|--------|------------------|
| Open source projects | How they organize modules, name things, handle errors |
| Your team's PRs | Patterns and idioms your team uses |
| Libraries you depend on | How the API is designed, how edge cases are handled |
| Old code you wrote | What you'd do differently now (sign of growth) |

## Spaced Repetition

| Interval | Action |
|----------|--------|
| Day 1 | Learn concept, write notes |
| Day 3 | Review notes, try an exercise |
| Day 7 | Build something small with it |
| Day 14 | Apply to a real project |
| Day 30 | Teach someone else |

## Learning a New Language

1. **Syntax basics** — variables, control flow, functions, data structures
2. **Build and run** — compile/interpret, package manager, test runner
3. **Idiomatic patterns** — how do locals solve common problems?
4. **Ecosystem** — popular libraries, frameworks, tools
5. **Build a real project** — the fastest way to internalize

## Best Practices

- **Learn one deep thing at a time** — breadth comes after depth
- **Write down what you learn** — this handbook exists for exactly this reason
- **Teach to learn** — explaining a concept reveals gaps in your understanding
- **Timebox exploration** — 30 minutes of research, then build or move on
- **Revisit fundamentals** — every few years, the "basics" of a topic have evolved

## Common Mistakes

| Mistake | Problem | Fix |
|---------|---------|-----|
| Tutorial hell | Lots of tutorials, no real code | Build something, struggle through it |
| Too many technologies at once | Shallow knowledge everywhere | Pick one stack, go deep first |
| Only coding at work | Slow growth | Side projects, open source contributions |
| Not reading others' code | Limited perspective | Review PRs, read OSS code |
| Comparing to others | Unproductive anxiety | Compare yourself to where you were last month |
